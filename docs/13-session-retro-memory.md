# Session, retrospective and memory signals

> **Status:** Normative design  
> **Purpose:** Capture the JEV use case where agent/session activity is classified into useful short-term, retrospective and long-term signals.

## Why this exists

A long agent session contains far more information than should become memory.

Useful signals are often buried inside:

- user corrections;
- accepted/rejected decisions;
- repeated failed approaches;
- new constraints;
- changed preferences;
- successful techniques;
- unresolved work;
- important evidence.

The goal is not "summarize the whole transcript."

The goal is:

> identify meaningful episodes, classify their future value, and let deterministic policy decide persistence.

## Classification scopes

Initial scope vocabulary:

- **ephemeral** — only useful for the immediate interaction;
- **short_term** — useful for the active task/session;
- **retrospective** — useful for analysing how the work went;
- **long_term** — potentially reusable in future work;
- **discard** — no persistence value.

These are not storage backends. They are semantic categories.

## Work on episodes, not entire sessions

A session can contain unrelated topics and temporary mistakes.

Prefer bounded episodes such as:

- one user correction plus the affected decision;
- one tool failure/retry sequence;
- one accepted architecture decision;
- one approval;
- one finished subtask;
- one repeated pattern.

Episode boundaries can initially be deterministic:

- user turn;
- semantic event close;
- tool call/result group;
- approval resolution;
- plan step completion;
- explicit correction;
- task completion.

Later, JEV can help judge whether adjacent events belong to the same episode.

## Candidate extraction

Do not send every token to memory classification.

First create candidate signals from meaningful runtime events.

Examples:

~~~ts
type MemoryCandidate = {
  id: string;
  episodeId: string;
  kind:
    | "user_correction"
    | "accepted_decision"
    | "rejected_approach"
    | "constraint"
    | "preference"
    | "failure_pattern"
    | "successful_pattern"
    | "unresolved_work"
    | "other";
  summary: string;
  evidenceRefs: string[];
};
~~~

The summary may be deterministic for structured events or generated by an LLM when synthesis is genuinely needed.

## JEV questions

Given a candidate plus evidence/context, useful independent questions include:

- Is this an accepted decision rather than merely a proposal?
- Is this a stable project/user constraint?
- Is this likely to matter outside the current task?
- Is this mainly useful for retrospective analysis?
- Is this a repeated failed approach?
- Is this already represented by existing memory?
- Does it contradict an existing persisted signal?
- Is evidence sufficient to persist?
- What scope best fits: ephemeral / short_term / retrospective / long_term / discard?

## Example: architecture decision

Episode:

~~~text
Proposal: use Durable Objects immediately.
Discussion: local-first preferred; avoid cloud coupling until session coordination proves necessary.
Decision: local modular monolith now; Durable Objects is a later option.
~~~

Candidate:

~~~json
{
  "kind": "accepted_decision",
  "summary": "Start local-first; do not require Durable Objects until real session-coordination needs justify them."
}
~~~

Expected classification:

- accepted decision: high;
- long-term project relevance: high;
- evidence sufficient: high.

Policy can persist this into a project decision artifact/ADR.

## Example: failed debugging attempt

Episode:

~~~text
Agent tried approach A three times.
Same error remained.
User switched to approach B, which worked.
~~~

Candidate:

~~~json
{
  "kind": "failure_pattern",
  "summary": "Approach A repeatedly failed for this failure mode; approach B resolved it."
}
~~~

Possible scopes:

- retrospective;
- long-term if broadly reusable;
- discard if it was an environment-specific transient issue.

## Example: user correction

Episode:

~~~text
Assistant assumed requirement X.
User: "No, I specifically don't want X; use Y."
~~~

This can be more valuable than an earlier inferred preference because it is explicit corrective evidence.

JEV can classify whether the correction is:

- local to one task;
- a durable project constraint;
- a stable preference.

## Deterministic persistence policy

JEV does not directly write long-term memory.

Example policy:

~~~ts
if (candidate.scope === "long_term" &&
    candidate.evidenceSufficient >= 0.8 &&
    candidate.isAcceptedDecision >= 0.8) {
  persistProjectSignal(candidate);
}
~~~

Exact thresholds need evals.

Some categories may require explicit human review before long-term persistence.

## Dedupe and contradiction

Before writing a long-term signal:

1. retrieve likely related existing signals;
2. ask bounded questions about duplicate/contradiction;
3. apply deterministic merge/review policy.

Do not silently overwrite an older decision simply because a newer candidate has a higher model confidence.

Preserve chronology/evidence.

## Relationship to repository artifacts

For this project, durable agent collaboration should prefer checked-in artifacts when appropriate:

- ADRs for architecture decisions;
- docs for stable design;
- eval fixtures for behavioral lessons;
- issue/PR notes for task-specific handoffs.

JEV memory classification can identify what deserves one of those artifacts.

The repository, not one model's private chat history, is the shared collaboration surface.

## Retrospective output

A retro can aggregate classified episodes into:

- decisions made;
- corrections;
- failed approaches;
- useful patterns;
- unresolved work;
- follow-ups.

An LLM may generate the final readable retrospective from structured signals.

JEV helps decide what belongs in it.

## Inspector view

A session inspector could show:

~~~text
Episode 14
  type: user correction
  candidate: "voice provider must remain pluggable"
  scope probabilities:
    ephemeral      0.01
    short_term     0.04
    retrospective  0.21
    long_term      0.72
    discard        0.02

  evidence sufficient: high
  duplicate: low
  policy: propose long-term project signal
~~~

Again, this exposes decisions/evidence, not hidden chain-of-thought.

## Initial implementation

Do not build a vector memory system first.

Start with:

- SQLite memory_candidates table;
- structured episode references;
- JEV classification;
- simple exact/keyword retrieval for dedupe experiments;
- Inspector UI.

Add embeddings/vector search only when a real retrieval problem demonstrates the need.
